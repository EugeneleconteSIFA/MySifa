MySifa · Serveur MCP

Quels outils construire pour capter les données

MySifa expose aujourd'hui 233 tables métier et 63 tables du miroir RVGI. Le réflexe naturel — un outil par table — produit un serveur inutilisable. Un MCP puissant tient en une douzaine d'outils à forte densité métier : le modèle sait déjà écrire du SQL, ce qu'il ignore ce sont les pièges de la base et les chiffres qui font référence. Voici le périmètre, dans l'ordre où il se construit.

Socle Les quatre outils qui portent tout le reste à faire en premier
  • mysifa_schema Le catalogue sémantique Pas le DDL brut : le sens des tables, les clés de jointure et les pièges déjà payés — corbeille = 0, le montant se lit dans htn, dates à tronquer à 10 caractères, code1/2/3 en texte, jointure entête obligatoire sur les lignes.
  • mysifa_query SQL en lecture seule SELECT uniquement, LIMIT forcé, délai maximal, paramètre source: production | rvgi. C'est l'outil qui rend inutiles cinquante outils spécialisés.
  • mysifa_resolve Résoudre une entité Dossier, OF, référence produit, matière et laize, fournisseur, machine : rend l'identifiant canonique et ses liens. Sans lui, chaque requête part sur un identifiant deviné.
  • mysifa_metric Les chiffres qui font foi Calculés par le backend, jamais par le modèle. La saisie opérateur reste le repère n°1 : si le MCP recalcule dans son coin, il devient le troisième écran avec le troisième chiffre.
Métier Ce qui se demande mieux en conversation qu'en écran valeur immédiate
  • rvgi_reconcile Contrôle de véracité Chaîne commande → dossier → colisage → BL → facture → échéance, MySifa confronté à RVGI. Le chantier est déjà ouvert ; c'est la question type qu'on ne pose pas à un écran.
  • dossier_contexte Un dossier, d'un bloc Saisies, arrêts et seuils franchis, matières consommées, info prod, mapping OF, scan rattaché. Une réponse au lieu de six requêtes.
  • produit_memoire Tout sur une référence Séries passées, savoirs opérateurs, non-conformités, temps réel face au prévu. La mémoire produit devient interrogeable au lieu d'être seulement consultable.
  • anomalies La liste des trous Dossiers clos sans code matière scanné, OF non rattachés, mappings à valider, fiches non vérifiées par l'ADV, alertes maintenance en attente, certifications fournisseurs qui expirent. De quoi alimenter un point du matin automatique.
  • traca_fsc Remonter la chaîne Matière → dossier → BL, et surtout produire la preuve. L'audit à blanc se joue sur cet outil.
Écriture Peu d'outils, tous tracés après le socle
  • tache_create La conversation devient une tâche Une demande formulée à l'oral atterrit dans /taches avec son module, son type et son assignation.
  • reunion_note Déposer un compte-rendu Notes et actions décidées d'un point de production, ou une info prod de dossier depuis le Retour de prod.
Trois règles d'écriture  ·  passer par l'API HTTP avec clé scopée, jamais d'INSERT direct en base  ·  tracer dans le journal des actions avec un acteur MCP identifiable  ·  jamais rien vers RVGI, le sens d'écriture reste unique.
Ce qui sépare un MCP correct d'un MCP puissant
Passer par FastAPILire le fichier SQLite en direct, c'est perdre les droits, la trace et l'unicité de la logique métier.
Rendre l'URL de l'écranChaque réponse porte son lien MySifa : un chiffre doit toujours ouvrir l'écran déjà filtré.
Hériter d'un utilisateurLe MCP a exactement les droits de l'écran. Paie, RH et documents du personnel hors périmètre par défaut.
Exposer des ressourcesRègles data, dictionnaire de tables et conventions lus comme ressources MCP, sans brûler un appel d'outil.
Prévoir des promptsAudit à blanc FSC, point de production de la veille, contrôle de véracité RVGI : des parcours figés, prêts à lancer.
Répondre compactTableaux denses plutôt que JSON verbeux, avec un budget de lignes. C'est ce qui décide si l'outil tient sur 50 000 lignes.
